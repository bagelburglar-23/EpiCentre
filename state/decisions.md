# Decisions

Settled. Treat as constraints, not open questions. Re-litigating these wastes
session time.

**To overturn a decision, supersede it with a new numbered entry. Never edit
or delete the old one.** The supersession history is the point — it shows what
changed and why, which is how you avoid re-deciding the same thing in six
months.

## Active

| id | decision | rationale |
|---|---|---|
| D-04 | Unit conventions must be stated explicitly | Caught a textbook silently switching delta-as-dollar-ratio vs lambda/elasticity mid-argument. General principle: a framework that shifts underneath an argument invalidates it. |
| D-06 | Agents *propose* writes to `state/*.md`; Lucas makes them | Prevents silent drift and confabulated facts in the human-maintained record. Does **not** apply to app code or the database. |
| D-08 | **No desk content, ever** | Bank records and surveillance obligations; this app is off-system. No positions, client names, risk figures, P&L, internal hostnames, network paths, add-in filenames. |
| D-09 | SQLite + Drizzle for application data | **Supersedes D-05.** An app needs queries, filtering, and joins. Markdown cannot do them. Single-user means SQLite will never be the bottleneck. |
| D-10 | No module imports another module | The entire guarantee that feature #12 costs what feature #2 cost. Coupling between modules is how a one-day feature becomes a three-day refactor. Shared code lives in `lib/`. |
| D-11 | Single-user. No user table, roles, permissions, or multi-tenancy | One password, one cookie. Most web guidance assumes customers; that advice is a tax here, not a benefit. |
| D-12 | The app does not own alerting — it exports `.ics`, Google Calendar fires | "Never miss a birthday" was the original goal. Web push on iOS is the least reliable channel available; a homemade notifier would be strictly worse than a calendar that already works. |
| D-13 | Server actions, not API routes | Layer count is the velocity metric. Writing an endpoint for your own front-end adds a serialization boundary for nothing. |
| D-14 | Migrations generated by drizzle-kit, committed, never hand-edited | Hand-edited schemas are the second-largest source of refactoring time after layer count. No single-user exception. |
| D-15 | Hosting: the phone-facing instance runs on the Hostinger KVM 2 VPS from Phase A; reachable only over a Tailscale tailnet, nothing public | **Supersedes the "Hosting" open item.** The VPS already exists and is paid for. Tailscale gives a real HTTPS cert and PWA-installable origin with zero public attack surface — the right posture given D-08. Dev stays on `localhost`; code moves dev→prod by git, data does not move. |
| D-16 | Agent integration is a standing design constraint. Agents run as **separate processes/containers on the VPS** and reach EpiCentre only through an authenticated HTTP capability interface (tailnet or VPS-localhost), published via module manifests | The endgoal is EpiCentre as a self-built agent host. Designing for it now costs almost nothing (see ARCHITECTURE "Agent integration"); retrofitting it later means touching every module. **Never** by importing a module, running in-process, or direct DB access — that recreates the coupling D-10 exists to prevent. D-13 governs the app's *own front-end* only; an external agent is a distinct consumer that legitimately needs a transport boundary. Agent bearer tokens are config, not users — D-11 stands. |
| D-17 | Module Drizzle schemas are discovered by a `drizzle-kit` glob (`modules/**/schema.ts`), not re-exported through a central `lib/schema.ts` | Keeps "adding a module touches exactly two shell files" (ARCHITECTURE rule 3) literally true. Cost: lose Drizzle relational-query sugar (`db.query.x.findMany({ with })`), which D-10 forbids across modules anyway; intra-module relations use explicit joins. |

## Open

Not yet decided, deliberately:

- **Sync across devices.** One SQLite file on the VPS, for now. Multiple
  devices already read it over the tailnet; a second *writer* is what needs
  thought.
- **Offline writes.** Shell caching is easy; write conflicts are not.
- **Agent trigger model, blast radius, and approval flow.** Whether agents run
  on a schedule / on events / on demand; whether they touch only EpiCentre data
  or the outside world; whether they write directly or propose-and-confirm
  (D-06 for `state/*.md` is the precedent). Closed enough to design the surface
  (D-16), open on the semantics until the agent phase.
